               R-TYPE APPLICATION-LAYER NETWORK PROTOCOL

Status of This Memo

   This document is a project-internal specification.  It is not an
   IETF standards-track document.  Distribution is unlimited.

Abstract

   This document specifies the application-level binary protocol used
   between the R-Type game client (r-type_client) and server
   (r-type_server).  It defines the packet format, opcode table,
   connection lifecycle, versioning rules, and error-handling policy.

   A developer with no access to the source code should be able to
   implement a compatible client or server by reading this document
   together with the transport specification (transport.md).

   For byte-by-byte packet layouts, see Packet Reference (packets.md).

1.  Introduction

   R-Type is a networked, horizontal-scrolling shoot-'em-up supporting
   1 to 4 simultaneous players.  The protocol is split into two layers:

   Transport layer  Handled by the network library.  Deals with TCP
                    framing, UDP binding, keepalives, and timeouts.
                    Documented in transport.md.

   Game layer       This document.  Carries application messages
                    (lobby, inputs, world state, chat) on top of the
                    transport layer.

   The protocol is entirely binary.  No human-readable encoding is
   used.  All integers are little-endian unless stated otherwise.

   The client-server model is authoritative server: all game logic
   runs on the server.  The client sends inputs and renders the world
   state that the server broadcasts.

2.  Conventions

2.1.  Notation

   u8, u16, u32   Unsigned integers of 8, 16, 32 bits, little-endian.
   i16            Signed 16-bit integer, little-endian, two's
                  complement.
   u8[N]          Fixed-size byte array of N bytes.
   LE             Little-endian byte order.

   All offsets are zero-based and expressed in bytes.  "Reserved"
   fields MUST be set to 0 by the sender and MUST be ignored by the
   receiver.

2.2.  Requirements Language

   The key words MUST, MUST NOT, SHOULD, and MAY in this document are
   to be interpreted as described in RFC 2119.

2.3.  Packet Diagrams

   Packet diagrams show fields from left (lowest offset) to right
   (highest offset).

    0               1               2               3
    0 1 2 3 4 5 6 7 0 1 2 3 4 5 6 7 0 1 2 3 4 5 6 7 0 1 2 3 4 5 6 7
   +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
   |    magic[0]   |    magic[1]   |    version    |    opcode     |
   +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

3.  Protocol Architecture

3.1.  Two-Layer Design

   +-----------------------+       +-----------------------+
   |     Game Client       |       |     Game Server       |
   |  Game layer (this doc)|       |  Game layer (this doc)|
   |  +-----------------+  |       |  +-----------------+  |
   |  | Packet builder  |  |       |  | Packet builder  |  |
   |  +-----------------+  |       |  +-----------------+  |
   |        |  ^           |       |        |  ^           |
   |        v  |           |       |        v  |           |
   |  +-----------------+  |       |  +-----------------+  |
   |  | INetworkClient  |  |       |  | INetworkServer  |  |
   |  +-----------------+  |       |  +-----------------+  |
   +-----------+-----------+       +-----------+-----------+
               |                               |
               |   TCP (Reliable)              |
               +===============================>
               |   UDP (Unreliable)            |
               +===============================>

   The network library is opaque to the game: it only exposes
   send(bytes, channel) and poll() -> events.  The game layer never
   touches sockets directly.

3.2.  Channels

   Reliable     TCP.  Used for handshake, lobby, and game events
                that must arrive in order.

   Unreliable   UDP.  Used for player inputs and world state sent
                every game tick.

3.3.  Game Phases

   The protocol defines three successive phases per session:

   Handshake    Version negotiation immediately after TCP connection.
   Lobby        Room creation, joining, and ready-state management.
   In-game      Real-time exchange of inputs and world state over UDP.

   Opcodes are only valid in the phases listed in Section 6.  A
   message received in the wrong phase MUST be silently dropped.

4.  Protocol Versioning

   Every game message starts with a 4-byte header:

      magic[0] = 0x52  ('R')
      magic[1] = 0x54  ('T')
      version  = 0x01
      opcode   = <opcode>

   The magic field allows quick validation.  The version field is the
   protocol version.

   Version negotiation:

   (1) The client sends HELLO with client_version set to 0x01.
   (2) The server rejects any HELLO where client_version != 0x01 by
       closing the TCP connection.
   (3) Once the server sends WELCOME, both sides agree on version
       0x01 for the session.

   Future versions increment the version byte.  A server supporting
   version N MAY accept clients announcing N-1 (backward
   compatibility), but this is not required.

5.  Connection Lifecycle

   The full lifecycle, including the UDP binding procedure, is
   described in transport.md Section 2.

   From the game layer's perspective:

   Client                                   Server
     |                                        |
     |-- TCP connect -----------------------> | (transport)
     |<-- Welcome [ClientId, token] --------- | (transport)
     |                                        |
     |-- HELLO (0x01) ---------------------> | Handshake
     |<-- WELCOME (0x02) ----------------- - |
     |                                        |
     |-- LOBBY_LIST_REQ (0x10) -----------> | Lobby
     |<-- LOBBY_LIST (0x11) ------------- - |
     |-- LOBBY_CREATE (0x12) OR             |
     |   LOBBY_JOIN (0x13) ---------------> |
     |<-- LOBBY_UPDATE (0x15) ----------- - |
     |-- LOBBY_READY (0x14) -------------> |
     |<-- GAME_START (0x20) ------------- - |
     |                                        |
     |-- [UDP open] -----------------------> | (transport)
     |-- PLAYER_INPUT (0x60) [UDP] -------> | In-game
     |<-- WORLD_STATE (0x70) [UDP] ------ - |
     |                                        |
     |<-- GAME_OVER (0x30) [TCP] --------- - |
     |-- [UDP close] ----------------------> | (transport)
     |-- LEAVE (0x40) [TCP] -------------> |
     |<-- TCP closed ----------------------- |

6.  Opcode Table

   Opcode  Name             Dir    Channel     Phase
   ------  ---------------  -----  ----------  ----------------
   0x01    HELLO            C->S   Reliable    Handshake
   0x02    WELCOME          S->C   Reliable    Handshake
   0x10    LOBBY_LIST_REQ   C->S   Reliable    Lobby
   0x11    LOBBY_LIST       S->C   Reliable    Lobby
   0x12    LOBBY_CREATE     C->S   Reliable    Lobby
   0x13    LOBBY_JOIN       C->S   Reliable    Lobby
   0x14    LOBBY_READY      C->S   Reliable    Lobby
   0x15    LOBBY_UPDATE     S->C   Reliable    Lobby
   0x20    GAME_START       S->C   Reliable    Lobby -> In-game
   0x30    GAME_OVER        S->C   Reliable    In-game -> Lobby
   0x40    LEAVE            C->S   Reliable    Any
   0x50    CHAT             Both   Reliable    Lobby + In-game
   0x60    PLAYER_INPUT     C->S   Unreliable  In-game
   0x70    WORLD_STATE      S->C   Unreliable  In-game

7.  Error Handling

7.1.  Malformed Packets

   A packet is considered malformed if any of the following hold:

   o  Its total length is shorter than 4 bytes (the header).
   o  magic[0] != 0x52 or magic[1] != 0x54.
   o  version does not match the negotiated version.
   o  The opcode is unknown.
   o  The payload is shorter than the minimum required for the opcode.
   o  A field value is outside its defined range.

   Malformed packets MUST be silently dropped.  The receiver MUST NOT
   close the connection or send an error reply.  This prevents a
   misbehaving peer from forcing a disconnect.

7.2.  Wrong Phase

   A valid packet received in the wrong phase (e.g., PLAYER_INPUT
   during the lobby) MUST be silently dropped.

7.3.  Transport-Layer Errors

   The transport layer handles connection drops, UDP timeouts, and
   write-queue overflows autonomously.  When it delivers a
   Disconnected event, the game layer discards all state for that
   ClientId.  The game layer never needs to handle raw socket errors.

8.  Security Considerations

8.1.  Token-Based UDP Authentication

   Every client-to-server UDP datagram is prefixed with
   [ClientId u32][token u32] by the transport layer.  The token is a
   32-bit cryptographically random value generated per TCP session
   (std::random_device).  A datagram with an unknown ClientId or a
   mismatched token is dropped before the game layer ever sees it.

8.2.  Input Validation

   The game layer MUST validate every field before acting on it:

   o  entity_id values in WORLD_STATE not in the known entity table
      MUST be ignored.
   o  player_index in GAME_START outside [0, player_count) MUST cause
      the client to disconnect.
   o  CHAT messages longer than 256 bytes MUST be truncated or
      dropped.

8.3.  Denial of Service

   o  The server accepts at most 64 simultaneous TCP connections
      (enforced by the transport layer).
   o  UDP datagrams larger than 1200 bytes are dropped by the
      transport layer before reaching the game layer.
   o  A TCP write queue exceeding 1 MiB per peer causes the session
      to be closed by the transport layer.

8.4.  Authoritative Server

   The server is the sole authority on game state.  Clients send only
   inputs (PLAYER_INPUT).  Any client that attempts to send game-state
   packets over UDP has those datagrams dropped because their opcode
   does not match 0x60.

9.  Port Assignment

   Protocol  Default Port  Notes
   --------  ------------  ----------------------------------
   TCP       4242          Client connects here first.
   UDP       4242          Same port; server multiplexes.

   The server binds both TCP and UDP to the same port.  The client
   learns the UDP port from the WELCOME packet's udp_port field,
   which allows the operator to choose a different port at startup.
