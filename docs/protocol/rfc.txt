               R-TYPE APPLICATION-LAYER NETWORK PROTOCOL

Status of This Memo

   This document is a project-internal specification.  It is not an
   IETF standards-track document.  Distribution is unlimited.

Abstract

   This document specifies the application-level binary protocol used
   between the R-Type game client (r-type_client) and server
   (r-type_server).  Messages are encoded with Protocol Buffers.  It
   defines the message envelope, message table, connection lifecycle,
   versioning rules, and error-handling policy.

   A developer with no access to the source code should be able to
   implement a compatible client or server by reading this document
   together with the transport specification (transport.md).

   For the fields of every message, see Packet Reference (packets.md)
   and the schema common/proto/rtype.proto.

1.  Introduction

   R-Type is a networked, horizontal-scrolling shoot-'em-up supporting
   1 to 4 simultaneous players.  The protocol is split into two layers:

   Transport layer  Handled by the network library.  Deals with TCP
                    framing, UDP binding, keepalives, and timeouts.
                    Documented in transport.md.

   Game layer       This document.  Carries application messages
                    (lobby, inputs, world state, chat) on top of the
                    transport layer.

   The protocol is entirely binary.  No human-readable encoding is
   used.  Game messages are encoded with Protocol Buffers (proto3
   binary wire format, [PROTOBUF]); the transport layer adds its own
   little-endian headers around them.

   The client-server model is authoritative server: all game logic
   runs on the server.  The client sends inputs and renders the world
   state that the server broadcasts.

2.  Conventions

2.1.  Notation

   uint32, sint32, bool, string, enum
                  Protocol Buffers scalar types, encoded as defined
                  by the protobuf wire format (varints, zigzag for
                  sint32, length-prefixed strings and messages).
   u8, i16        Logical range of a field carried as uint32 or
                  sint32 (protobuf has no 8- or 16-bit integers).
                  The receiver MUST reject a value outside the range.
   #N             Protobuf field number N.

   "Reserved" bits MUST be set to 0 by the sender and MUST be ignored
   by the receiver.

2.2.  Requirements Language

   The key words MUST, MUST NOT, SHOULD, and MAY in this document are
   to be interpreted as described in RFC 2119.

2.3.  Message Envelope

   Every game payload is exactly one serialized Envelope message:

      message Envelope {
          oneof message {
              PlayerInput player_input = 1;
              WorldState  world_state  = 2;
              Hello       hello        = 16;
              ...
          }
      }

   The field number of the oneof case identifies the message, like an
   opcode.  An Envelope with no case set, or with a case unknown to
   the receiver, is malformed (Section 7.1).

3.  Protocol Architecture

3.1.  Two-Layer Design

   +-----------------------+       +-----------------------+
   |     Game Client       |       |     Game Server       |
   |  Game layer (this doc)|       |  Game layer (this doc)|
   |  +-----------------+  |       |  +-----------------+  |
   |  | Packet builder  |  |       |  | Packet builder  |  |
   |  +-----------------+  |       |  +-----------------+  |
   |        |  ^           |       |        |  ^           |
   |        v  |           |       |        v  |           |
   |  +-----------------+  |       |  +-----------------+  |
   |  | INetworkClient  |  |       |  | INetworkServer  |  |
   |  +-----------------+  |       |  +-----------------+  |
   +-----------+-----------+       +-----------+-----------+
               |                               |
               |   TCP (Reliable)              |
               +===============================>
               |   UDP (Unreliable)            |
               +===============================>

   The network library is opaque to the game: it only exposes
   send(bytes, channel) and poll() -> events.  The game layer never
   touches sockets directly.  The packet builder is the codec of
   common/ (protocol::encode / protocol::decode); protobuf types never
   leave it.

3.2.  Channels

   Reliable     TCP.  Used for handshake, lobby, and game events
                that must arrive in order.

   Unreliable   UDP.  Used for player inputs and world state sent
                every game tick.

3.3.  Game Phases

   The protocol defines three successive phases per session:

   Handshake    Version negotiation immediately after TCP connection.
   Lobby        Room creation, joining, and ready-state management.
   In-game      Real-time exchange of inputs and world state over UDP.

   Messages are only valid in the phases listed in Section 6.  A
   message received in the wrong phase MUST be silently dropped.

4.  Protocol Versioning

   The protocol version is PROTOCOL_VERSION = 1.  It is carried by the
   Hello message only; other messages carry no header.

   Version negotiation:

   (1) The client sends Hello with version set to 1.
   (2) The server rejects any Hello whose version differs by closing
       the TCP connection.
   (3) Once the server sends Welcome, both sides agree on version 1
       for the session.
   (4) The client MUST send Hello within 5 seconds of the TCP
       connection.  Otherwise the server closes the connection.

   Compatible changes do NOT bump the version: adding a field to a
   message, or adding a new message to the Envelope.  Older receivers
   skip unknown fields and drop unknown messages.  Field numbers MUST
   never be reused or renumbered, and a field's type MUST never change.

   Breaking changes (removing or changing the meaning of a field)
   increment PROTOCOL_VERSION.  A server supporting version N MAY
   accept clients announcing N-1, but this is not required.

5.  Connection Lifecycle

   The full lifecycle, including the UDP binding procedure, is
   described in transport.md Section 2.

   From the game layer's perspective:

   Client                                   Server
     |                                        |
     |-- TCP connect -----------------------> | (transport)
     |<-- Welcome [ClientId, token] --------- | (transport)
     |                                        |
     |-- Hello (16) -----------------------> | Handshake
     |<-- Welcome (17) --------------------- |
     |                                        |
     |-- LobbyListRequest (32) -----------> | Lobby
     |<-- LobbyList (33) ----------------- |
     |-- LobbyCreate (34) OR               |
     |   LobbyJoin (35) ------------------> |
     |<-- LobbyUpdate (37) --------------- |
     |-- LobbyReady (36) ----------------> |
     |<-- GameStart (48) ----------------- |
     |                                        |
     |-- [UDP open] -----------------------> | (transport)
     |-- PlayerInput (1) [UDP] ----------> | In-game
     |<-- WorldState (2) [UDP] ----------- |
     |                                        |
     |<-- GameOver (49) [TCP] ------------ |
     |-- [UDP close] ----------------------> | (transport)
     |-- Leave (64) [TCP] ---------------> |
     |<-- TCP closed ----------------------- |

6.  Message Table

   #     Message           Dir    Channel     Phase
   ----  ----------------  -----  ----------  ----------------
   1     PlayerInput       C->S   Unreliable  In-game
   2     WorldState        S->C   Unreliable  In-game
   16    Hello             C->S   Reliable    Handshake
   17    Welcome           S->C   Reliable    Handshake
   32    LobbyListRequest  C->S   Reliable    Lobby
   33    LobbyList         S->C   Reliable    Lobby
   34    LobbyCreate       C->S   Reliable    Lobby
   35    LobbyJoin         C->S   Reliable    Lobby
   36    LobbyReady        C->S   Reliable    Lobby
   37    LobbyUpdate       S->C   Reliable    Lobby
   48    GameStart         S->C   Reliable    Lobby -> In-game
   49    GameOver          S->C   Reliable    In-game -> Lobby
   50    PlayerLeft        S->C   Reliable    Lobby + In-game
   64    Leave             C->S   Reliable    Any
   65    Chat              Both   Reliable    Lobby + In-game

   "#" is the field number of the message in the Envelope oneof.

7.  Error Handling

7.1.  Malformed Packets

   A payload is considered malformed if any of the following hold:

   o  It is empty or larger than 64 KiB.
   o  It is not a valid serialized Envelope (protobuf parse error:
      truncated varint, length past the end, invalid wire type,
      invalid UTF-8 in a string).
   o  The Envelope has no message set, or a message unknown to the
      receiver.
   o  An enum field holds an unknown value.
   o  A field value is outside its defined range, or a repeated field
      is longer than its defined maximum (see packets.md Section 8).

   Malformed packets MUST be silently dropped.  The receiver MUST NOT
   close the connection or send an error reply.  This prevents a
   misbehaving peer from forcing a disconnect.

7.2.  Wrong Phase

   A valid message received in the wrong phase or on the wrong
   channel (e.g., PlayerInput during the lobby, or any message other
   than PlayerInput sent to the server over UDP) MUST be silently
   dropped.

7.3.  Transport-Layer Errors

   The transport layer handles connection drops, UDP timeouts, and
   write-queue overflows autonomously.  When it delivers a
   Disconnected event, the game layer discards all state for that
   ClientId.  The game layer never needs to handle raw socket errors.

8.  Security Considerations

8.1.  Token-Based UDP Authentication

   Every client-to-server UDP datagram is prefixed with
   [ClientId u32][token u32] by the transport layer.  The token is a
   32-bit cryptographically random value generated per TCP session
   (std::random_device).  A datagram with an unknown ClientId or a
   mismatched token is dropped before the game layer ever sees it.

8.2.  Input Validation

   The game layer MUST validate every field before acting on it:

   o  Payloads are size-checked before parsing (64 KiB maximum), so
      parsing never allocates more than a bounded amount of memory.
   o  entity_id values in WorldState not in the known entity table
      MUST be ignored.
   o  GameStart with player_index outside [0, player_count) is
      malformed and dropped.
   o  Chat messages that are empty or longer than 256 bytes are
      dropped.
   o  The server ignores the client_id of a received Chat and fills
      in the sender's ClientId itself.

8.3.  Denial of Service

   o  The server accepts at most 64 simultaneous TCP connections
      (enforced by the transport layer).
   o  UDP datagrams larger than 1200 bytes are dropped by the
      transport layer before reaching the game layer.
   o  A TCP write queue exceeding 1 MiB per peer causes the session
      to be closed by the transport layer.

8.4.  Authoritative Server

   The server is the sole authority on game state.  Clients send only
   inputs (PlayerInput).  Any client that attempts to send another
   message over UDP has those datagrams dropped.

9.  Port Assignment

   Protocol  Default Port  Notes
   --------  ------------  ----------------------------------
   TCP       4242          Client connects here first.
   UDP       4242          Same port; server multiplexes.

   The server binds both TCP and UDP to the same port.  The client
   learns the UDP port from the Welcome message's udp_port field,
   which allows the operator to choose a different port at startup.
